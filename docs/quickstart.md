# Run Forge locally

Use Linux, Git, ripgrep, Python 3.13, uv 0.12.10, PostgreSQL and a Docker daemon
with user namespaces and cgroup v2 delegation. The normal execution default
requires rootless Docker, and tasks run as UID 1000 with disabled network and
bounded resources. This is a local single-user deployment.

Start in the cloned repository root:

```bash
uv python install 3.13
uv sync --frozen
cp .env.example .env
```

Edit `.env`: replace `FORGE_API_TOKEN` with a randomly generated local token, set
`FORGE_ALLOWED_REPO_ROOTS` to a JSON array of authorized absolute repository
directories, and configure the explicit `FORGE_DOCKER_HOST` socket. A token can be
generated with `uv run --no-sync python -c 'import secrets; print(secrets.token_urlsafe(32))'`.
Do not commit the populated `.env`, session files or model keys.

API, worker and migrations read `.env` through `Settings`. The standalone CLI has
its own lightweight `.env` loader for `FORGE_API_TOKEN` and `FORGE_API_URL`, so no
shell sourcing is required when invoking it from the repository root. Exported
values can still override `.env`; do not source the complete `.env` as shell code,
because JSON values such as allowed repository roots must retain their quotes.
Python settings accept either `OPENAI_API_KEY` or
`FORGE_OPENAI_API_KEY`, and the corresponding Anthropic and DeepSeek names
(`DEEPSEEK_API_KEY` / `FORGE_DEEPSEEK_API_KEY`). The offline demo needs no provider key.

## Start database and isolated execution

The supplied compose service creates a dedicated local PostgreSQL database on
port 55471. Use a different database/port when another development environment
already owns that service; do not run integration tests against a production DB.

```bash
docker compose -f deploy/compose.yaml up -d --wait postgres
uv run --no-sync alembic upgrade head
```

If you already have a suitable rootless daemon, use its socket. Otherwise the
project's Linux/systemd helper starts a separate user service:

```bash
bash scripts/rootless-daemon.sh
```

The helper needs Docker's standard rootless dependencies (`rootlesskit`,
`dockerd-rootless.sh`, `newuidmap`/`newgidmap`, configured subordinate IDs, and a
delegating user service manager). It does not switch Docker's global context.
Use the printed endpoint in `.env`; on the verified host it was
`unix:///tmp/forge-rootless-1000/docker.sock`. Do not start a second service with
the same name when `forge-rootless` is already running. The startup and observed
capabilities are recorded in [sandbox validation](validation/sandbox.md).

Build the trusted runner image into that daemon before submitting tasks:

```bash
export FORGE_DOCKER_HOST=unix:///tmp/forge-rootless-1000/docker.sock
docker --host "$FORGE_DOCKER_HOST" build -f docker/runner.Dockerfile -t forge-runner:dev .
```

Dependency installation happens during this trusted image build. Agent commands
cannot install dependencies from the network. Run submission freezes the actual
local image content ID, so `forge-runner:dev` is only a development lookup name.

## Public client demonstration: zero paid calls

Run this on an otherwise idle, dedicated Forge database with no other workers or
queued tasks. The demo starts its own API at port 18765 and launches a separate
production worker with `--once`. That worker claims the next eligible database
job, so a concurrently populated queue is not an isolated demonstration.

```bash
uv run --no-sync python scripts/demo.py \
  --docker-host "$FORGE_DOCKER_HOST" \
  --output .forge/demo/latest.json
```

The demonstration creates a committed source checkout under `.forge/demo/source`,
and unique private session configuration/data/log directories. It authenticates
through the public CLI, queues a repair, disconnects a watcher, starts the worker,
reconnects from the persisted event cursor, downloads the patch and verification
receipts over HTTP, and leaves the original checkout unchanged. It stops only the
API/worker processes it started. Existing project services are not terminated.

The defect is meaningful but small: composite cursor pagination drops events
sharing a timestamp at a page boundary. Six public unittest cases define ordering,
cursor exclusion, pagination completeness and input bounds. The offline script
explicitly supplies four calls: read source, apply an authored correction, run
focused tests, and propose completion. A separate read-only validation workspace
must pass the fixed public regression and target suites before the run is
`completed`/`verified`.

**This is an offline control-flow demonstration. The scripted correction is not
generated by a model, and its completion is not a model-quality score.** There are
no hidden benchmark tests or private evaluator reference patches in this demo.
See [public-client evidence](validation/public-client.md) for the actual run.

## Run the API and worker yourself

For ordinary usage use the same `.env` file, database, config root and data root
in these separate terminals:

```bash
# Terminal 1
uv run --no-sync uvicorn forge.api.main:app --host 127.0.0.1 --port 8765
```

```bash
# Terminal 2
uv run --no-sync forge-worker
```

```bash
# Terminal 3, from the repository root.
# From the repository root, the CLI reads its token and URL directly from .env.
uv run --no-sync forge project /absolute/allowed/repository --name example --profile python-tests
uv run --no-sync forge run PROJECT_ID 'Fix the reported defect' --config YOUR_CONFIG_ID --base-commit COMMIT
uv run --no-sync forge watch RUN_ID
uv run --no-sync forge status RUN_ID
uv run --no-sync forge diff RUN_ID
```

Profiles live in `configs/repo_profiles/ID.yaml`. They pin allowed patch paths,
protected tests, validation commands and the prebuilt image. The supplied
`python-tests` profile is an example: adapt it to the repository before registering
a project. A supported, explicitly pinned acceptance target is required for
`verified`; passing only general regression tests is reported as `regression_only`.

Use `forge message RUN_ID 'Additional constraint' --key UNIQUE_KEY` to append a
constraint at a safe boundary. Use `forge status` to inspect exact pending
operations and `forge approve APPROVAL_ID --version N` only after reviewing them.
`forge cancel` requests cancellation; it does not immediately certify that an
active process stopped. `forge resume RUN_ID --version N` reconciles existing
operations rather than starting a fresh model run. Full contracts are in
[the API documentation](api.md).

## Explicit live model runs

Copy `configs/runs/openai.example.yaml` or `anthropic.example.yaml` to a new config
ID. Replace placeholder model IDs, capabilities and every required price using
your enabled account and current official provider documentation. Record the
price source/version and set a bounded `run.budget.max_cost_usd`. Add the provider
key to `.env` or the environment. Example capability numbers are not current
model guarantees; missing prices must not be interpreted as zero cost.

To use the same public cursor task with that manually configured provider:

```bash
uv run --no-sync python scripts/demo.py \
  --docker-host "$FORGE_DOCKER_HOST" \
  --live-config configs/runs/YOUR_CONFIG_ID.yaml \
  --authorized-budget-usd 1.00 --timeout 900 \
  --output .forge/demo/live-observation.json
```

This command makes paid provider requests and is intentionally manual. The
configuration's maximum cost must fit the explicit authorization. A single live
observation remains a demonstration, not a benchmark result. No live run is part
of ordinary tests or the default demo.

If the live config requires write approval, the demo prints a private
`client.env` path while keeping its API available. In another terminal source
that file, inspect `forge status RUN_ID`, and approve or deny the exact operation
with the shown version. The demo does not approve on your behalf. A deadline or
failure retains logs and requests cancellation of its own run.

## Separate evaluation worker

For the fixed DeepSeek experiment authorized at USD 10, use the
[cumulative-budget campaign command](evaluation-deepseek.md). It accounts for
both provider smoke runs and all evaluation trials in one persistent ledger.

Quality evaluation requires the authorized private evaluator store described in
[evaluation.md](evaluation.md); a public clone does not contain private grader
tests/reference patches. Missing private data is an explicit dependency, and is
not replaced with the demo's tests.

Set `FORGE_ENABLE_EVALUATIONS=true`, `FORGE_EVAL_PRIVATE_DIR` and appropriate
allowed repository roots in `.env`. Prepare a trusted experiment YAML under
`configs/experiments/` that refers to a dataset, live run config and repo profile.
Restart the API after changing settings. Keep a normal task worker running and
start the independent evaluator in another terminal:

```bash
uv run --no-sync forge-eval-worker
```

An explicitly authorized submission can then use:

```bash
uv run --no-sync forge eval submit EXPERIMENT_CONFIG_ID \
  --experiment UNIQUE_EXPERIMENT_ID --tasks TASK_ID \
  --conditions B0 --repeats 1 --budget 1.00
uv run --no-sync forge eval status EVALUATION_ID
```

The total experiment budget and per-run limits both apply. This command submits
work, not a completed report; inspect the final state and retained trial evidence.

## Checks and CI

```bash
uv run --no-sync pytest tests/unit tests/contract tests/review -q
env FORGE_TEST_DATABASE_URL="$FORGE_DATABASE_URL" \
  FORGE_TEST_DOCKER_HOST="$FORGE_DOCKER_HOST" FORGE_TEST_IMAGE=forge-runner:dev \
  FORGE_RUN_PUBLIC_CLIENT=1 \
  uv run --no-sync pytest tests/integration/test_public_client.py -q
```

The integration command requires exported database/socket values and the same
otherwise idle dedicated DB rule as the demo. Every normal CI job has empty
provider keys. The second CI job is explicitly named **PostgreSQL + rootful Docker
development boundary**: hosted GitHub runners use their standard rootful daemon
with non-root containers, and that job cannot establish rootless acceptance.
Local rootless evidence is separate. CI uploads JUnit and the public fixture's
sanitized result only, not `.env`, private session directories or grader stores.

CI uses uv 0.12.10, Python 3.13 and `uv sync --frozen`. Its checkout/setup-uv action
pins follow the current [official uv Actions guide](https://docs.astral.sh/uv/guides/integration/github/);
artifact retention uses [GitHub's official upload-artifact action](https://github.com/actions/upload-artifact).
All three action commit SHAs were additionally checked against GitHub's official
tag-reference API on 2026-09-07; exact references are recorded in the public-client
validation report.

Compatibility and migration checks:

- [FastAPI's version guidance](https://fastapi.tiangolo.com/deployment/versions/) recommends pinning tested versions and checking tests before an upgrade. A checked-in frozen lock is the reproducibility mechanism here; do not claim an upgrade occurred when none was needed.
- [LangGraph v1 migration guidance](https://docs.langchain.com/oss/python/migrate/langgraph-v1) describes the prebuilt `create_react_agent` deprecation and Python 3.10 minimum. Forge already uses a custom graph on Python 3.13. A migration to a higher-level agent factory is not required for this work and could obscure its explicit state/receipt logic.
- [The Postgres checkpoint README](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md) documents connection/setup expectations. Keep the existing checkpoint initialization path; telemetry shutdown must not change checkpoint durability semantics.
- OpenTelemetry 1.44 removes its deprecated Events API and moves declarative configuration into an experimental package; [the release notes](https://github.com/open-telemetry/opentelemetry-python/releases/tag/v1.44.0) distinguish those changes from ordinary tracing. This task should use the existing tracing API rather than adopt experimental configuration solely for novelty.

## Prioritized, bounded engineering change

The inspected baseline `src/forge/telemetry.py` attaches a `SimpleSpanProcessor` to both JSONL and OTLP HTTP export. With OTLP configured, span completion invokes the exporter on the worker's calling thread. A slow collector can therefore consume event-loop time needed by lease renewal, cancellation and task execution. This is a code-supported failure hypothesis; numerical severity requires a measured baseline.

The [OpenTelemetry tracing specification](https://opentelemetry.io/docs/specs/otel/trace/sdk/#onendspan) explains that `OnEnd` runs synchronously within span completion and should not block. The [Python 1.44.0 processor implementation](https://github.com/open-telemetry/opentelemetry-python/blob/v1.44.0/opentelemetry-sdk/src/opentelemetry/sdk/trace/export/__init__.py) offers a bounded batching processor. Its `export_timeout_millis` is not passed through to `export`; it must **not** be mistaken for a network deadline. Configure the OTLP exporter timeout explicitly and test the behavior actually obtained.

1. **P0 — isolate remote trace export from the async worker.** Use bounded background export, explicit network timeout, and asynchronous best-effort shutdown with an explicit OTLP request timeout (arbitrary Python export threads cannot be forcibly terminated). Preserve local trace evidence and existing span correlation/redaction contracts. This supplies direct evidence for the resilience and agent-failure-handling requirements at Zip and Netic. Acceptance: collector stall, collector failure, queue pressure and shutdown cannot synchronously stall span completion or leave an unbounded queue; existing trace contents remain compatible.
2. **P0 — measure the operational consequence with a reproducible fault benchmark.** Compare the existing synchronous path with the new path using identical injected collector delay, span count and a 5 ms asyncio ticker. Record Python/dependency/OS/CPU information, parameters, per-repeat results, queue configuration, ticker scheduling delay and span-emission latency. The ticker measures event-loop responsiveness; its percentiles are not PostgreSQL worker-heartbeat percentiles. Real worker heartbeat renewal belongs to separate functional acceptance under exporter blocking, with its own database-backed evidence. Separate successful delivery, dropped spans and collector failures. Acceptance: baseline and changed mode both run; the ticker remains responsive during exporter blocking; all published numbers can be recomputed from saved results; actual heartbeat renewal passes its independent functional check. A local delayed exporter is fault injection, not a production outage or cloud load test.
3. **P1 — maintain evidence and operating instructions.** Document that telemetry delivery is best effort, bounded buffering may lose spans, and the PostgreSQL action/usage ledger remains authoritative for execution recovery. Update only validated facts in portfolio/bank entries, linking the measurement and tests. Leave any unexecuted network, runtime, cloud or shutdown scenario explicitly unverified.

The checked experience-bank inventory already includes AsyncFlow TaskMgr, VelaServe, Quorum Market, Telemetry Loss Clinic and Runbook Atlas, covering related task execution, serving, failure handling, telemetry and operational evidence. Forge's distinct contribution is **protecting an AI application's control path from an observability dependency**: remote trace export must not interfere with its worker's lease renewal, cancellation or action/usage evidence boundaries. This application-specific interaction supplies the value beyond the capabilities already represented in the other projects. It should not be presented as another collector implementation, a system-wide throughput improvement, a guarantee against all blocking I/O, or a measured reduction in LLM cost/latency. Local JSONL I/O and other synchronous work require their own evidence before broader claims.

This document is the research and acceptance plan, not a completion report. Actual implementation choices and verified measurements belong in the resulting validation artifact.
